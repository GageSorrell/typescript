How hard would it be, with Codex and Claude Code, to modify current TypeScript (`typescript@7.0.2`) such that the following things are added,



- an accessor operator `::` for accessing namespaces, static properties of classes, and things in barrel exports (for example, the exported contents of a module that is imported with `import * as Foo` syntax, or an imported thing that was exported as `export { Foo, Bar, ... };` or `export * from "./Foo.js";` syntax), such that the dot operator that TypeScript currently uses for these becomes disallowed (error by default, with a `tsconfig.json` setting added that allows for permitting the dot operator, but with a warning, such that warnings like this can also be disabled via a separate `tsconfig.json` setting under `compilerOptions`)
- the pipe operator `|>` which is a binary operator that takes a value for its LHS, and a function whose argument vector of a single argument such that the left-hand value can be passed to the RHS function.  Pipe operator calls can be chained together such that, for example, `Foo |> Bar |> Baz` is valid if `Foo` is a value, `Bar` is a function that maps values such as `Foo` to values that can be accepted by a function `Baz`, and this expression ultimately evaluates to the output of `Baz` when given the input that is the return value of `Bar` when `Bar` is given `Foo`
- the pipe operator should support functions in its RHS whose argument vectors have more than one argument, by supplying multiple arguments in the LHS by defining the LHS value as: the unzip operator, followed by an array literal containing the values that make up the argument vector passed to the RHS function.  If the developer wishes to use an existing array of values for the LHS, the developer can simply write `...[ ...Foo ] |> Bar` for an array of values `Foo` to be used for the argument vector of a function `Bar`, such that the length and element types of `Foo` satisfy the argument vector of `Bar`.
- First-class support for partial application via the comma operator, such that if a function `Bar` is defined like `const Bar = (A, B, C) => { /* ... */ };`, then a function `Baz` can be defined like `const Baz = Baz(Alice, , Charlie)` such that `Baz` then is a function that takes a single argument whose type is the type of the argument `B` of `Bar`'s argument vector, and calling `Baz` with a value `Bob` corresponding to `B` is handled by internally calling `Bar` with argument vector `Alice, Bob, Chalie`.  When using an extra comma to "skip" an argument (to define a partially-applied function), such a comma should be able to be optionally prefixed with an underscore, which aims to improve readability but does not affect behavior.  A value (function, constant, variable, whatever) named `_` that exists in a scope in which `_,` is used for partial application should *not* cause an error: the forked TypeScript transpiler should be able to recognize that this instance of the underscore in `_,` is not referring to a variable (or function, whatever) named `_` that is in the same scope, if such a value exists.
- first-class support for equipping objects with the ability to be used as the right-hand argument with the pipe operator, by equipping the object with a function property whose key is a `unique symbol` provided by `typescript`, such that the function can be overloaded to support multiple types and arities
- Operator overloading such that free functions can be defined whose arguments can be primitives (or any other type).  All operators should be overloadable, and arity should be preserved for all possible overloads.  Semantics for issues like precedence and scope should borrow from C++'s operator overloading
- Custom literals similar to those in C++, to be able to define constructor functions that take the number literal as an argument, for example, a `cm` constructor function to use as a custom literal such as `50_cm`, such that `cm` is defined like `const cm = CustomLiteral("cm", (Self: number) => { /* ... */ });` where `CustomLiteral` is provided by TypeScript and does not need to be imported, and returns a branded type that can be referenced as a regular `number` as well.  TypeScript would also be extended somehow to allow for defining conversion functions, whose scope and precedence match the corresponding semantics for custom literal constructor functions
- higher-kinded types, such that generic types can be defined such that their type arguments can be required to be generic themselves, such that, for a given type argument, the type can be required to be generic of a given arity, and each type argument of the generic type that this type argument extends can have its possible types narrowed by using `extends`.  It should be possible to define a generic type with a type argument that can be any type that has a given number of type arguments, without specifying anything else about the type: for example, a developer should be able to require a type argument to be of a type that has a single type argument, regardless of what the generic type is, such that if it is just required that the type argument is of a generic type with a single type argument, then `Array` and `Set` would both be valid, but `Map` would not.  It should also be possible to impose requirements for the types of the inner type arguments, so that `Array` and `Set` both satisfy a constrained type argument, but the element type of the given `Array` or `Set` must extend some given type, such that for example `Array<string>` and `Set<string>` both work, but not `Array<number>` or `Set<number>`, for example.
